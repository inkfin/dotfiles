# 中文编辑

适用于中文回复、公告、技术说明和文章。目标是让读者顺着文字理解事情。保留作者原有的语气和信息；没有正面风格样本时，默认平实、连贯，不主动模仿作家或营销号。

## 先处理整段

先确认读者需要知道什么、需要做什么，再看现有段落是否方便理解。去 AI 味允许合并和调序，不等于摘要。用户要求轻改或保留格式时，缩小改动范围。

- 短通知通常可以直接交代变化，接着解释使用条件和操作。不要强套“为什么做／想法／实现／优势／总结”的提纲；长文有检索需要时仍可用标题。
- “背景。……”“想法。两层，别混。”这类标签加碎句，常把本来连续的说明拆成演讲提词卡。将标签里的有效信息写进正文，补上必要的条件和动作。
- 多段连续写“比 X 好”“不做 X，只做 Y”，容易变成推销或辩解。把各句提供的机制、差异和限制归到相关功能旁。用户确实要求比较时，保留有同一比较依据的列表或表格。
- 操作步骤、配置字段和互斥选项适合列项。背景、原因和解释通常适合段落。不要把所有列表压成一堵长文，也不要为每句话安排一个项目符号。
- 检查“结论＋解释＋换句话再结论”的复述，只删重复信息。文章在最后一条有用信息处结束即可。

## 再处理句子

| 常见问题 | 编辑判断 |
| --- | --- |
| “两层，别混”“现在就能用，不求人”“出事才喊人”接连出现 | 读者需要知道哪两种用途、什么条件触发、具体执行什么。把已有答案写出来，避免训话和故作干脆。单独一句口语未必需要改。 |
| “等的是指标，不是墙上的钟” | 找出对照中实际说明的差异，例如按指标条件等待与按固定时刻执行。直接解释，保留原本必要的区别。 |
| “真正的价值在于”“说到底”“核心只有一句话” | 若只是为普通事实造势，删除引导语。不要换成另一句宣告。 |
| “说实话”“讲真”“你没看错”或连续自问自答 | 没有实际转折时直接说事情。保留作者确有用途的问句，不批量替换成口头禅。 |
| 句句短促、每句单独成段 | 将条件、动作、原因接成完整句子。长短由信息决定，不按字数或固定比例交替。 |
| 连续四字短语、三连排比或对仗收尾 | 展开其中实质不同的信息，合并同义复述。不要为了拆“三点”丢掉第三件事。 |
| “对……进行……”“使得……得以……”和多层“的” | 尽量用直接的动词，理清修饰关系。中文上下文已经明确的主语可以省略，不必句句补“它”或“我们”。 |
| “赋能、闭环、抓手、生态”代替说明 | 从原文找出谁做什么、对象是谁、结果是什么。没有依据就用较朴素的原意，不能自行补案例或数字。控制系统的“闭环”等准确术语照留。 |
| “显著提升”“彻底解决”“不会把平台打爆” | 保留有依据的效果，按原文机制说明能做到的程度。不要把降低风险写成绝对保证；涉及实质判断变动时另行说明。 |
| “挂、拉、喊、扛”等连续代替动作 | 按读者熟悉程度保留必要口语；会混淆失败、停止、重启、调用、通知时，写具体动作。不要把技术名词一律口语化。 |

这些是上下文线索，不是词语禁令，也不能用来判定一段话必定由 AI 写成。

## 技术说明不能改丢什么

动笔前在心里记下原文的事实和条件，改完逐项核对：谁触发、何时触发、执行什么、需要先配置什么、失败如何处理。特别留意“默认、仅、需手动、尚未、可能”等限定。

代码块、命令、参数、字段名、状态枚举、路径、版本、数值单位和链接目标按原文保留。不要擅自翻译或规范化标识符；例如 PR 不等同于代码审查，`pending` 不能只剩“等待”。原文中的疑似技术错误需要单独指出，不能借润色悄悄修正。

重要的否定条件仍要写清，例如“进程未启动时不会自动通知”。删除的应是空转的对照修辞，不能连安全边界、前置条件一起删掉。没有核验的功能描述仍然只是原文的说法，不要加“实测”“保证”等背书。

中文使用正常的全角标点，可保留中文引号和必要括号。合理的冒号、破折号、顿号不是错误。处理的是反复用标点造停顿或强调；命令中的 `--`、JSON 引号和 Markdown 语法不受散文规则影响。

## 对照示例

以下片段用于校准编辑判断，不是所有文章都要套用的句式。

### 把提词卡接回说明

原文：

> 想法。两层，别混。人还在对话里：wait-event。同一条 agent loop 堵住，等到了再继续。不喊第二个 agent。没人盯着：watch-events --loop。后台按项目配置轮询，出事才起 tcodex / tclaude / cursor-agent（命令自己配）。

改写：

> 在对话中等待某个条件时，用 `wait-event` 暂停当前 agent loop，条件满足后由同一个 agent 继续处理，不会启动第二个 agent。无人值守时，可以运行 `watch-events --loop`，让它按项目配置在后台轮询，触发后再调用配置好的 `tcodex`、`tclaude` 或 `cursor-agent` 命令。

检查：保留了两种用途、同一 agent 继续和命令需配置的条件，没有把“后台轮询”写成平台推送。

### 保留必要的边界

原文：

> overnight 守护不是开机自带的。拷 .gameair/avatar_events.example.json → .gameair/avatar_events.json，改 agent_commands 和要盯的 hook，然后自己挂。没跑这个进程，流水线挂了不会自动喊人。

改写：

> 夜间守护需要手动配置并启动。先将 `.gameair/avatar_events.example.json` 复制为 `.gameair/avatar_events.json`，修改 `agent_commands` 和要监控的 hook，再启动守护进程。进程未运行时，流水线失败不会自动触发通知。

检查：前置条件和否定句都保留了。如果原文后面还有启动命令，终稿必须连同命令交付。

### 本来清楚的句子可以不改

> 探针只返回 `pending`、`met`、`emergency`、`unavailable`。轮询默认间隔为 30 分钟，带随机抖动；探针之间间隔 2 秒，失败后延长轮询间隔。

这里的枚举、数字和分号有实际用途。不要为了换一种说法改成“探针汇报情况，隔一阵再检查”，也不要替这段补充未给出的退出码。

## 交付前读一遍

先逐项检查事实、命令和限定条件是否还在，再连读全文：是否仍有连续标签短句、故作亲近的口头禅、反复自我辩护或金句收尾？是否只是替换了词，原来的模板还在？若终稿比原文更含糊或更难读，撤回那项风格修改。

普通回复直接采用这些判断；改写任务默认只交付终稿。用户要求分析时再解释主要改动，不自动输出自评分、检测器分数或多版草稿。
